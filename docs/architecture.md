# Architecture

## Folders

All application code is under `src/`; the project root holds only tool config
(`package.json`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`,
`components.json`), `public/` and `docs/`. `out/` (the built static site) and
`.next/` (dev cache) are generated by the tools, ignored by git and safe to
delete.

| Location | Responsibility |
|---|---|
| `src/app/` | Routes only: `page.tsx` files, root layout, metadata, `not-found.tsx`, `sitemap.ts`, `robots.ts`, icons |
| `src/components/ui/` | shadcn/ui primitives (generated, then restyled) |
| `src/components/layout/` | `SiteHeader`, `DesktopNavigation`, `MobileNavigation`, `SiteFooter` |
| `src/components/sections/` | Page sections and the `PageSections` renderer (text, split, overlay card, feature grid, info table, events, testimonials, booking panel, image band…), headings, prose, links |
| `src/components/media/` | `ResponsiveImage`, `ImageGallery` + `Lightbox`, `ImageCarousel`, `Banner`, `VideoPlayer` |
| `src/components/forms/` | Field components, submit button, status message, field styles, and one folder per site form (schema + component), shared field and date rules, submission hook |
| `src/components/events/` | Event page ticket section (`EventTickets`) |
| `src/components/news/` | News index, cards, article body renderer |
| `src/data/` | **All site data**: page content (`pages/*.ts`), image list (`images.ts`), articles (`blog.ts`), events (`events.ts`), site details (`site.ts`), menus (`navigation.ts`) |
| `src/lib/` | Code only: content loaders and schemas, News and event loaders, asset lookup, link resolver, form submission adapters and endpoints, menu helpers, route list, SEO helper (`siteUrl`), utilities |
| `src/styles/` | `globals.css`: Tailwind, brand tokens, shadcn variable mapping |
| `public/` | Image files (`images/`), videos (`videos/`), PDFs (`documents/`) |
| `docs/` | This documentation |

Imports use the `@/` alias, which points at `src/` (`@/lib/news` is
`src/lib/news.ts`).

## Content flow

```
src/data/pages/<page>.ts ──► src/lib/content/pages.ts (Zod parse) ──► src/app/<route>/page.tsx ──► PageSections
src/data/blog.ts ──► src/lib/news.ts (Zod) ──► /blog, /blog/page/[page], /post/[slug] ──► ArticleBody (blocks → React)
src/data/pages/home.ts ──► src/lib/content/pages.ts (Zod parse at build) ──► src/app/page.tsx
src/data/images.ts ──► src/lib/assets.ts getImage(id) ──► ResponsiveImage ──► next/image (unoptimized) ──► /images/<dir>/<name>.webp
src/data/site.ts, src/data/navigation.ts ──► SiteHeader / SiteFooter
```

1. Page copy lives in `src/data/pages/<page>.ts`, copied word for word from
   the live site.
2. Each file is typed with `satisfies ContentPageInput` (so the editor flags
   mistakes), and `src/lib/content/pages.ts` validates it with the schemas in
   `src/lib/content/schema.ts`. Invalid content fails the build with the file and
   field path.
3. Page files (`src/app/**/page.tsx`) pick the content apart and compose section
   components. Image fields are ids from `src/data/images.ts`, resolved with `getImage()`.
4. `next build` renders everything to static HTML in `out/`.

## Server and Client Components

Server Components (no `"use client"`): the root layout, every page, all of
`src/components/sections/`, `SiteHeader`, `SiteFooter`, `ResponsiveImage`. They read
the content files and the image list at build time; that data never ships to the
browser except as rendered HTML/props.

Client Components, kept small:

| Component | Why it is a client component |
|---|---|
| `DesktopNavigation` | hover/focus/keyboard state for dropdowns |
| `MobileNavigation` | open/close state, Radix Dialog |
| `NewsletterForm`, `ContactForm` | React Hook Form state |
| `src/components/forms/*`, `src/components/ui/field`, `checkbox`, `label`, `sheet` | used inside the above |

The footer is a Server Component that renders the `ContactForm` island; the
home page renders the `NewsletterForm` island inside a server `CardSection`.
`PageSections` is a Server Component; only `ImageGallery`/`Lightbox`,
`ImageCarousel`, `TestimonialCarousel` and the enquiry forms hydrate. Inline
Markdown is parsed at build time; `fs` and the image list are only imported by server
modules.

## Key decisions

- **Static export (`output: "export"`).** No server features are used
  (no Server Actions, route handlers, rewrites or runtime image optimisation).
  `cacheComponents`/`partialPrefetching` from the scaffold were removed: they
  configure runtime caching that a fully static site does not use.
- **One image file per photo.** Static export has no image optimiser, so
  `next/image` runs with `unoptimized: true`: each photo is a single WebP
  (1280px wide for most, 1920px for large and full-width photos) that every
  screen size loads. Containers size and crop it with CSS (`fill` +
  `object-fit: cover`, or full width with its own aspect ratio).
- **Custom desktop navigation instead of shadcn NavigationMenu.** On the live
  site, parent items (Home, Weddings, Stay, Café) are links that also open a
  dropdown. Radix NavigationMenu triggers are buttons, so a parent could not
  stay a link. The custom menu opens on hover and on keyboard focus, closes on
  Escape and blur, and reopens with ArrowDown.
- **Pointer-aware desktop variant.** `desktop:` in `globals.css` means
  "≥1024px wide *and* a fine pointer". Touch tablets of any width get the
  menu button, because hover dropdowns cannot be used reliably by touch.
- **Content validated with Zod.** The same library as the forms; editors get a
  precise build error instead of a silently broken page.
- **`cn` with brand tokens.** shadcn 4.22 merges classes with the `cn` package.
  `src/lib/utils.ts` registers the custom `text-*` sizes so they replace a
  component's default size instead of being treated as colours. shadcn
  components import `cn` from `@/lib/utils`; components added later with
  `npx shadcn add` import from `"cn"` and must be switched (see
  design-system.md).

- **Section-based content pages.** Content pages are ordered lists of typed
  sections (`src/lib/content/sections.ts`) rendered by one server component, so
  editors can reorder or edit sections in the `.ts` content files while each section type stays a
  small component. Home predates this and is composed by hand.
- **Third-party widgets are not embedded.** Sonas forms became native forms;
  Bookalet and TeamUp became links to the providers; event pages are rebuilt
  here with a ticket request form (no payments); voucher "Buy now" opens an
  email to the café. Nothing links to the old Wix site. The one embed is the OpenStreetMap map on event
  pages (no key, no cookies).

## Adding a page

The current way is described in content-and-assets.md ("Adding a page"): a
content `.ts` file with sections, one import in `src/lib/content/pages.ts` and a
three-line route file. The older hand-composed approach (used by Home) is
below.

Example: a hypothetical Gift card page.

1. Create `src/data/pages/gift-card.ts`, copying text verbatim from the live
   page.
2. Add a schema in `src/lib/content/schema.ts` (reuse `headingSchema`,
   `paragraphSchema`, `pageMetadataSchema`) and a loader in
   `src/lib/content/pages.ts`:
   ```ts
   export const getGiftCardPage = () => parse(giftCardPageSchema, giftCard, "src/data/pages/gift-card.ts");
   ```
3. Add its images (content-and-assets.md, "Adding or replacing an image").
4. Create `src/app/gift-card/page.tsx`:
   ```tsx
   const page = getGiftCardPage();
   export const metadata = pageMetadata(page.metadata);
   export default function GiftCardPage() {
     return <SplitContentSection heading={page.intro.heading} paragraphs={page.intro.paragraphs}
       image={getImage(page.intro.image)} imageSide="left" />;
   }
   ```
5. Add the path to `sitePaths` in `src/lib/routes.ts` so it enters the
   sitemap.
6. Run `npm run check`.
